Hexo 博客管理工具：把每天敲的命令做成桌面程序

发表于2026-11-21|更新于2026-11-21|应用开发
|总字数:3593|阅读时长:14 分钟|浏览量:

含大肥鱼生成内容

写博客最烦的环节不是写。

是写完之后的动作：开 PowerShell，cd 到博客目录，hexo clean，hexo generate，等半分钟，再 hexo deploy，再等半分钟。想改个副标题，还得打开 VS Code，翻到 _config.yml，在两百多行里找那个键，顺便小心别把缩进弄坏。

这两个半分钟里什么都干不了，出错也只有一个退出码可看。于是把整套动作收进一个窗口：能点的就不敲，能预览的就不猜。

工具做完了，五个页面，一个 exe，双击就能用。

它管哪些事

页面 干什么
站点与目录 选博客根目录，校验 _config.yml 和 source/_posts，检查 Node 和 hexo 在不在
文章管理 列出全部 Markdown，按标题、标签、分类搜，新建、编辑、删除
命令控制台 clean / generate / server / deploy 四个按钮，日志实时刷
配置管理 17 个常用字段可视化修改，改前自动备份
发布到 GitHub 生成、推送、开启 Pages，最后甩给你一个地址

路径存在 %AppData%\HexoBlogManager\settings.json，下次打开自己加载。这个位置是刻意的，不放程序目录，免得到时候装在 Program Files 里写不进去。

选目录这一步比想象中容易出错，最典型的误选是把 source 当成博客根目录，因为那看起来最像「文章所在的地方」。所以现在如果检测到当前目录没有 _config.yml、但上一级有，会直接告诉你选错层级了，以及正确的根目录是哪个。

技术上是怎么搭的

.NET 10 + WPF，C#，零 NuGet 依赖。没有 MVVM 框架，没有 YamlDotNet，没有 Markdown 库。你机器上有 .NET SDK 就能编译。

选 WPF 而不是 Electron，主要是体积和启动速度。同一套功能用 Electron 做，包体积动辄一百多兆，冷启动也要等一会儿；现在这个是自包含单文件，59 MB，双击就出来。代价是 XAML 写起来啰嗦，样式得自己搓。

32 个 .cs 加 9 个 .xaml，一共约 1.1 万行。分三层：

目录 职责
Models 纯数据：文章元信息、站点信息、设置、发布配置
Services 20 个服务类：进程执行、front-matter 解析、YAML 读写、GitHub API、发布流程
Views 五个页面加一个编辑器窗口

服务层基本不碰 UI，例外是 Markdown 渲染和 ANSI 配色，这两个天生就跟显示绑在一起，硬拆开反而别扭。

Windows 上绕不开的几个坑

中文乱码不是编码设置的问题

直接 Process.Start("hexo", "generate") 有个麻烦：控制台里中文全是问号。问题不在 Encoding.UTF8，在代码页。Windows 控制台默认 GBK（936），hexo 检测到终端是 GBK 就按 GBK 输出，你按 UTF-8 解码当然乱。

解法是执行前先切代码页：

chcp 65001 是切到 UTF-8，>nul 是把”Active code page: 65001”这行提示吞掉。还有一个细节：hexo 在 Windows 上不是 exe，是 hexo.cmd，所以必须过一层 cmd.exe，不能直接 CreateProcess。

中文路径和空格路径

这块反而是最简单的。只要不把路径拼进命令行字符串，而是塞进 WorkingDirectory，空格和中文都不会出问题，不需要加引号也不需要转义。命令行参数才需要处理，路径不需要。

测试时我专门复制了一份博客到 D:\测试 博客\带空格的博客，中文加空格，一切正常。

Hexo 的彩色输出会变成乱码

日志区第一版长这样：

\u001b[32m 是 ANSI 转义码，控制台认识它，WPF 的 RichTextBox 不认识。写了个 AnsiText 解析器，只处理 SGR 序列（以 m 结尾那种），把 16 色调色板映射成 VS Code 终端的配色，逐段生成彩色的 Run。这样 Hexo 原本的绿色 INFO、黄色 WARN 都还原了。

同一个类还提供 Strip 方法去掉全部转义码，用在两处：判断日志级别，以及复制到剪贴板。后者是被逼的，因为提取 hexo server 的预览地址时正则把残留的 [24m 一起抓进去了，地址变成了 http://localhost:4000[24m，点开当然是 404。

退出码是 0，但其实失败了

这个坑值得单独说。

hexo deploy 没装 deployer 插件时，日志里明明白白一行红色的 ERROR Deployer not found: git，但进程退出码是 0。我一开始只看退出码，界面显示”执行完成”，然后我去刷新网页，发现什么都没变。

现在改成两条都看：退出码是 0，但日志里出现 ERROR 级别的行，就给黄色警告加一段针对当前命令的排查清单，而不是绿色的”成功”。颜色误导人比报错更烦。

.git 不能放在 public 里

发布功能第一版是这么做的：在 public 目录里 git init，提交，force push 到 gh-pages。跑起来没问题，直到我点了一次”清理缓存”。

hexo clean 会删掉整个 public。而 git 的对象文件是只读的，删除时报 ENOENT，public 目录删到一半卡住。从那以后 clean 就没成功过。

后来改成跟 hexo-deployer-git 一样的做法：在博客根目录建一个 .deploy_git，把 public 里的文件同步过去，在那边提交推送。public 保持干净，clean 恢复正常，附带好处是提交历史变成增量的，不用每次重建仓库。

同步逻辑里还有个小坑。清空目标目录时我先删多余文件，再删空目录，结果刚 git init 出来的 .git/objects、.git/refs 是空目录，被当成垃圾删了，后面 commit 直接失败。现在遇到 .git 相关路径一律跳过。

front-matter 只能改，不能重写

这一条是我给自己定的硬规矩。

很多工具的思路是：解析 front-matter 成对象，改完再序列化回去。听着合理，实际会把用户自定义的字段全吃掉。Hexo 的 front-matter 没有固定 schema，Butterfly 认 cover、top_img、sticky，别的主题认别的键，插件还可能有自己的字段。序列化只能输出你认识的那些。

所以我做的是行级替换。保存时记住每个键对应的原始行块，只替换托管的 7 个字段（title、date、updated、tags、categories、top、comments），其余的连顺序带缩进原样写回：

写完一定会补上缺的托管字段，但绝不会碰你的 cover。

解析这边兼容四种写法：多行列表、行内 [a, b]、单值标量 categories: 未分类、数字 top: 2。单值标量那条是自检抓出来的，原本只认列表，而这种写法在 Hexo 里完全合法，结果就是分类读成空的。

编辑器左边写右边预览，防抖 350 毫秒。预览是自己写的 Markdown 转 FlowDocument，支持标题、代码块、行内代码、列表、引用、链接、图片。表格和数学公式没做，预览只要能看清文章结构就够了，再多就是另写一个渲染器。拖图片进编辑器会自动存到 source/images/yyyy/MM/，顺手插入链接。

删除走的是 Windows 回收站，不是直接抹掉。误删还能捞回来，这个比二次确认弹窗实在。

配置识别：照 Hexo 的合并规则来

配置页最初是让你自己填的，空白表单。这不对，你的配置明明就在硬盘上躺着。

但要”自动读取”就得先搞清楚 Hexo 到底读哪些文件。翻了一遍 hexo/dist/hexo/index.js 和 load_theme_config.js，结论是：

  1. _config.yml 是主配置
  2. _config.production.yml 之类是环境覆盖，优先级高于主配置
  3. 主题配置是 deepMerge(主题自带的 _config.yml, 根目录的 _config.butterfly.yml)

第三条最容易踩。根目录那份只是覆盖层，你没写的键继续用主题默认值。所以界面上一个字段显示什么，取决于它在哪一层被定义。

每个字段带一个状态，一共四种：

状态 含义 保存时
已读取 在要写入的那个文件里读到了 照常写
继承 只存在于主题默认配置里 不写，除非你改过
被覆盖 值来自 _config.production.yml，改主配置不生效 提示你改哪儿
未设置 哪个文件都没有 用默认值，不往文件里塞空键

“不写”这条是硬要求。第一次点保存时，如果从主题默认继承来的那几十项全被写进 _config.butterfly.yml，这个文件会从几十行涨到几百行，以后主题升级还得逐条对照。我用 md5sum 验证过：打开页面直接保存，两个配置文件的哈希一个字节都没变，也不产生备份文件。

读取部分的容错做得比较厚。新写了一个扁平解析器，产出”路径 → 值”的字典，遇到问题只记警告不抛异常：

  • Tab 缩进按 2 空格算（YAML 规范禁止 Tab，但很多人手写会混进去）
  • 缺冒号的行跳过，继续读下一行
  • 重复键提示后一个会被前一个覆盖
  • 引号没闭合也能读完
  • 多行文本块 | 和 > 正常处理
  • 编码先看 BOM，再试严格 UTF-8，失败按 GB18030 解码

最后一条是给老博客准备的。国内不少 _config.yml 是 GBK 存的，按 UTF-8 硬读出来中文标题全是方块，现在能正确解码，并在详情里注明”已按 GB18030 解码”。

写入还是走行级路径编辑，不重新序列化整个 YAML。注释、顺序、缩进都不动，保存前自动备份成 _config.yml.yyyyMMdd-HHmmss.bak，最多留 10 份。

这里也修过一个旧 bug：布尔值被当成”可能被误读的字符串”加上了引号，nav.fixed: true 被写成 fixed: "true"，在 YAML 里就成了字符串而不是布尔。主题读它的时候判断为真，看着能用，其实语义变了。

一键发布到 GitHub Pages

流程是十一步：校验 Token → 查仓库在不在（不在就问你要不要建 public 仓库）→ hexo clean → hexo generate → 同步到 .deploy_git → 写 .nojekyll → add → commit → force push → 开启 Pages → 算站点地址。

几个决定。

第一是不用 hexo-deployer-git。那个插件要改你的 _config.yml、要装 npm 包，出错只给一行报错，而且它不管”帮我把 Pages 打开”这一步。自己用 git 命令行加 REST API，主流程 690 行，API 客户端 359 行，出错能说清楚是哪一步。

第二是 Token 用 Windows DPAPI 加密存盘。%AppData% 下任何程序都能读，明文存等于把仓库写权限送人。DPAPI 的密钥由 Windows 按当前登录用户托管，程序里不存任何东西，配置文件被拷走也解不开。代价是换电脑要重填。

第三是日志里做 Token 脱敏。推送地址里带 Token，一旦打进日志就等于写进了文本文件。现在日志里永远是 https://***@github.com/...。

免费账号的 Pages 只能用于 public 仓库，私有仓库会提示但不拦你。刚推完访问 404 是正常的，GitHub 那边要构建一到两分钟。

测了多少

_selftest 是个独立控制台工程，直接链接主项目的源文件，176 项断言，跑一遍要几分钟。

覆盖范围 怎么测的
front-matter 解析与重建 四种写法、字段保真、中文标题、空 body
配置识别 缺失、Tab 缩进、缺冒号、重复键、引号未闭合、GBK、多文件覆盖、主题三处回落
写入安全 原样保存不改文件（比 md5）、不产生备份、布尔值不加引号
发布流程 本地 bare 仓库当远端，验证提交、force push、.nojekyll、中文文件名
GitHub API 本地 mock 服务，验证 401、建仓库、开 Pages、分支一致时不重复创建
回归 发布完再执行 hexo clean 是否仍然成功

发布相关的测试没有碰真实仓库，远端是 git init --bare 出来的本地目录，API 是本机起的一个假服务。整套流程跑通之后，我才拿真实的 GitHub 仓库推了这个项目本身。

没做完的部分

  • 预览只到结构级，不渲染表格和数学公式
  • 编辑已有文章不能改文件名，怕站内链接失效。要改名就重命名文件再打开
  • 拖进来的图片固定进 source/images/，没跟 post_asset_folder 联动，因为那个开关不是每个博客都开
  • 只支持 Windows。WPF 决定的，没打算改
  • 没做 CNAME 可视化，自定义域名得自己改配置
  • 部署历史会一直在 .deploy_git 里累积，量大了手动删掉，下次发布会重建

最后

仓库： tianqi-studio/hexo-blog-manager，MIT 协议。Release 里是自包含单文件，59 MB，解压双击就能跑，不依赖 .NET 运行时，但你本机得先有 Node 和 hexo，这个工具是调命令行，不是替代 Hexo。

如果你也在用 Hexo 加 Butterfly，这个 Hexo 博客管理工具可以拿去试试。跑不起来的话，大概率是路径选错，或者 hexo 不在 PATH 里，页面上的环境自检会直接告诉你缺哪个。
